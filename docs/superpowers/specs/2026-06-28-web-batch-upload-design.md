# Web 批量上传 MD 和图片设计

## 背景

Web 端当前已经支持在每个日期格子中上传单张图片和单个 Markdown 文件。图片上传会先保存到 PhotoPrism，再生成卡片并异步分析标签；Markdown 上传会读取文本、生成摘要和标签，再保存为 `type: "md"` 的卡片。

这次新增批量上传能力：用户可以在某一天的格子中一次多选图片和 `.md` 文件，系统把这些文件全部导入到被选择的那一天。目标是提升日常整理效率，同时保持现有卡片、搜索、详情和灵感册能力不变。

## 范围

### 包含

- Web 端日期格子新增一个混合“批量导入”入口。
- 文件选择支持 `multiple`。
- 一次选择中允许图片和 `.md` 混选。
- 用户在哪一天触发导入，所有文件都使用该日期格子的 `dayIndex` 和当前 `weekId`。
- 拖拽文件到日期格子时也支持多文件导入。
- 前端使用顺序队列逐个处理文件。
- 图片复用现有图片上传、存储、建卡和异步标签分析逻辑。
- Markdown 复用现有文本读取、摘要标签生成和建卡逻辑。
- 批量导入过程中展示进度和当前文件状态。
- 批量导入结束后展示成功和失败汇总。
- 单个文件失败不阻塞后续文件。

### 不包含

- 不按文件名、图片 EXIF 或创建时间自动分配日期。
- 不新增批次历史页面。
- 不新增失败重试按钮。
- 不支持文件夹递归上传。
- 不新增后端批量上传接口。
- 不新增 `import_batches` 或 `import_items` 数据表。

## 用户体验

### 入口

每个 `DaySlot` 提供一个主要的混合批量导入入口：

- 空日期格子中显示“批量导入”入口，允许选择图片和 Markdown。
- 已有卡片的日期格子右下角也显示同一个批量导入按钮。
- 文件选择器配置为 `accept="image/*,.md,text/markdown"` 并启用 `multiple`。

原有“粘贴截图”行为保持单图处理，不扩展为批量剪贴板导入。

### 分配规则

批量导入不做自动分发。用户从哪个日期格子触发上传，所有文件都导入到该日期：

- `weekId` 使用当前周。
- `dayIndex` 使用触发上传的日期格子。
- 图片和 Markdown 都保存为该日期下的卡片。

### 进度状态

导入开始后，日期格子显示批量进度：

- 总文件数。
- 已完成数量。
- 当前正在处理的文件名。
- 成功数量。
- 失败数量。

示例文案：

- `正在导入 3/8`
- `当前：moodboard.md`
- `已完成 6 个，失败 1 个`

导入结束后，如果全部成功，显示简短成功提示；如果存在失败项，显示失败文件名和原因。

## 文件处理规则

### 图片文件

图片文件继续复用现有图片流程：

1. 校验 `file.type.startsWith("image/")`。
2. 为 AI 分析生成较小的 JPEG 分析图。
3. 原图通过 `/api/store-image` 保存到 PhotoPrism。
4. 使用返回的 `imageUrl`、`thumbnailUrl`、`photoUid`、`photoHash` 创建图片卡片。
5. 先保存兜底标签，确保图片卡片尽快出现在界面上。
6. 后台异步调用 `/api/analyze-image`。
7. 如果分析返回标签，调用现有标签更新逻辑。

图片分析失败不算导入失败。只要图片已经保存并建卡成功，该文件就算导入成功；标签分析失败时保留兜底标签。

### Markdown 文件

Markdown 文件继续复用现有 Markdown 流程：

1. 接受 `.md` 文件名或 `text/markdown` 类型。
2. 读取文件文本。
3. 空内容不建卡，并记录为该文件失败。
4. 调用 `/api/summarize-md` 获取摘要和标签。
5. 如果摘要服务不可用，使用本地摘要兜底。
6. 创建 `type: "md"` 卡片，写入 `mdContent`、`mdSummary`、`mdName` 和标签。

## 错误处理

批量队列按顺序处理文件。某个文件失败后记录错误并继续处理后续文件。

常见错误：

- 不支持的文件类型：跳过并记录失败。
- Markdown 为空：跳过并记录失败。
- 图片读取失败：记录失败。
- 图片存储失败：记录失败。
- 卡片保存失败：记录失败。
- Markdown 摘要失败：不阻断导入，使用兜底摘要和标签。
- 图片标签分析失败：不阻断导入，保留兜底标签。

错误提示以文件名为单位，不展示完整堆栈，不暴露 token、密钥或后端返回的敏感细节。

## 数据库设计

本功能不新增批次表。最终数据仍然落在现有 `cards` 表中：

- 图片卡片继续使用 `image_url`、`thumbnail_url`、`photo_uid`、`photo_hash`、`terms`。
- Markdown 卡片继续使用 `type`、`md_content`、`md_summary`、`md_name`、`terms`。
- 所有卡片继续使用现有 `user_id`、`week_id`、`day_index`、`created_at` 字段。

当前 `cards` 表已经包含 Markdown 所需字段和搜索用 `terms_text`。实现时只允许做与现有 schema 兼容的小补强，例如补缺失字段或保证查询返回 Markdown 字段；不为批量导入增加新的持久化模型。

## 组件和边界

### `DaySlot`

`DaySlot` 负责用户交互和队列状态：

- 接收多文件选择和多文件拖拽。
- 按文件类型分发到图片或 Markdown 处理逻辑。
- 维护当前批次的进度、成功数、失败列表和提示文案。
- 保持单个粘贴截图逻辑不变。

### `App`

`App` 继续负责实际上传和建卡逻辑：

- `handleUploadImage` 处理单个图片文件。
- `handleUploadMd` 处理单个 Markdown 文件。
- 批量队列调用这些单文件函数，不复制业务逻辑。

### 服务端

服务端不新增批量接口。现有接口保持不变：

- `POST /api/store-image`
- `POST /api/analyze-image`
- `POST /api/summarize-md`
- `POST /api/db/cards`
- `PUT /api/db/cards/:id/terms`

## 性能和限制

队列按顺序处理，避免一次性并发打爆 PhotoPrism、AI 分析接口和数据库。

单个图片继续沿用后端 multer `25MB` 文件大小限制。前端可以在失败提示中展示文件过大或上传失败，但不在本次设计中新增复杂的大小预检和批量上限配置。

## 验证计划

- `npm run lint` 通过。
- 在 Web 页面选择某一天，多选多张图片，确认全部落到同一天。
- 在 Web 页面选择某一天，多选多个 `.md`，确认全部落到同一天。
- 混选图片和 `.md`，确认图片卡片和 Markdown 卡片都生成。
- 拖拽多个文件到日期格子，确认队列处理和日期归属正确。
- 选择不支持的文件类型，确认失败列表显示且其他文件继续导入。
- 上传空 Markdown，确认不建卡并显示失败原因。
- 模拟图片标签分析失败，确认图片卡片仍然存在并保留兜底标签。
- 搜索 Markdown 文件名、摘要和标签，确认仍然可检索。
- 打开图片详情和 Markdown 详情，确认显示正常。

## 实施顺序

1. 在 `DaySlot` 中改造文件输入为混合多选入口。
2. 增加批量队列状态和结果汇总。
3. 让文件选择和拖拽都调用同一套批量处理函数。
4. 图片文件复用现有单图处理函数。
5. Markdown 文件复用现有单 Markdown 处理函数。
6. 补齐错误提示和批量结束状态。
7. 运行类型检查，并在 Web 页面手动验证混选导入。
