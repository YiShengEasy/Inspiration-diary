# Inspiration Diary 全端媒体流量优化方案

## 1. 目标与范围

本方案同时覆盖：

- 微信小程序：灵感首页、日详情、搜索、灵感册、收藏、卡片详情和工具箱。
- Web：周视图、全部灵感、灵感册、卡片详情、组合卡和视频播放。
- 服务端与存储：Express API、阿里云 ECS、OSS 私有资源、后续 CDN。

目标是在不降低原图下载质量、不增加明显等待、不改变现有数据归属和鉴权模型的前提下，减少 OSS 下行流量、ECS 代理流量和客户端无效下载。

## 2. 当前基线与主要问题

### 2.1 生产素材基线

2026-07-10 对生产 PostgreSQL 只读统计：

| 类型 | 数量 | 总体积 | 平均体积 | 最大体积 | 存储位置 |
|---|---:|---:|---:|---:|---|
| 普通视频 | 5 | 102.0 MB | 20.4 MB | 73.9 MB | OSS |
| 绑定图片 | 0 | 0 | 0 | 0 | - |
| 组合参考图 | 3 | 5.7 MB | 1.9 MB | 1.9 MB | OSS |
| 组合生成视频 | 0 | 0 | 0 | 0 | - |

上述统计不包含 `cards` 表中的主图原文件，因此图片总量和主图流量会高于表中数字。

### 2.2 当前媒体链路

当前受保护媒体基本经过以下链路：

```text
小程序 / Web
  -> ECS /api/videos、/api/images、/api/objects
  -> ECS 获取 OSS 签名地址
  -> ECS 代理读取 OSS 内容
  -> ECS 再把内容传给客户端
```

这会同时消耗 OSS 外网流出和 ECS 下行带宽。服务端 `proxySignedObjectUrl()` 已经可以透传 `Range`，但小程序详情页在播放前调用 `wx.downloadFile` 下载完整视频，播放器无法利用 Range 做边播边取。

### 2.3 小程序现状

- `downloadAsset()` 对图片和视频统一调用 `wx.downloadFile`。
- 视频详情会等待完整视频下载后再渲染播放器。
- 灵感首页、日详情和灵感册单次最多请求 200 条卡片，并对结果执行并行媒体下载。
- 搜索一次最多 50 条，收藏一次最多 60 条。
- 多数 `<image>` 未启用懒加载。
- 工具箱部分固定宣传图和“我的”默认头像仍引用外部图片域名。
- 服务端已配置主图缩略处理 `image/resize,w_480/quality,q_80/format,webp`，但绑定图片、组合图和详情图没有形成统一规格。

### 2.4 Web 现状

- “全部灵感”和灵感册已经按每页 12 条分页，应保留。
- 普通图片卡优先使用 `thumbnailUrl`，但部分 `<img>` 未设置 `loading="lazy"` 和 `decoding="async"`。
- 当前周数据仍可能一次加载整周全部卡片及完整列表字段。
- 列表接口会返回 `mdContent`、`videoAssets`、`imageAssets` 等详情字段，列表首屏并不都需要。
- 图片详情直接使用大图地址；没有统一的“列表、详情、原图”三级规格。
- Web 视频已使用 `preload="metadata"`，但视频字节仍经过 ECS 代理。
- Vite 静态文件有内容哈希，但 Express 静态服务没有设置长期 immutable 缓存。
- Web 上传流程已经保留原图，并生成最大 600px 的 AI 分析副本，这一策略是合理的，应继续保留。

## 3. 优化原则

1. 原图只在用户主动下载时传输，浏览页面永远使用匹配屏幕尺寸的版本。
2. 视频点击后直接流式播放，不在播放前完整下载。
3. ECS 负责鉴权、元数据和签名，不代理大体积媒体字节。
4. 列表只返回列表字段，详情按需加载完整内容。
5. 首屏只加载可见资源，下一屏静默预取。
6. 保留原图和原视频，不以永久降低素材质量换取流量。
7. 所有改造可通过配置回退到现有 ECS 代理路径。

## 4. 统一媒体规格

建议由服务端根据用途生成短期 OSS 签名地址，并通过 OSS 图片处理实时输出以下规格：

| 规格 | 使用位置 | OSS 处理建议 | 目标体积 |
|---|---|---|---:|
| `thumb-240` | 小程序三列卡片、小封面 | `image/resize,w_240/quality,Q_70/format,webp` | 20-50 KB |
| `thumb-480` | 小程序日卡、Web 卡片、灵感册封面 | `image/resize,w_480/quality,Q_75/format,webp` | 40-100 KB |
| `detail-1280` | 小程序和 Web 图片详情 | `image/resize,w_1280/quality,Q_82/format,webp` | 150-350 KB |
| `poster-720` | 视频列表和播放前海报 | `video/snapshot,t_1000,f_jpg,w_720` | 50-150 KB |
| `original` | 用户主动下载 | 不处理 | 原始体积 |

阿里云 OSS 支持在读取时实时缩放、质量变换和 WebP 转换，无需长期保存多份派生文件：

- [OSS 图片缩放](https://help.aliyun.com/zh/oss/user-guide/resize-images-4)
- [OSS 图片质量变换](https://help.aliyun.com/zh/oss/user-guide/adjust-image-quality)
- [OSS 图片格式转换](https://help.aliyun.com/zh/oss/user-guide/convert-image-formats-2)

采用绝对质量 `Q`，避免原图本身已经压缩时继续按比例过度压缩。透明图片若不能接受 WebP/JPEG 背景变化，应保留 PNG 或使用支持透明通道的 WebP。

## 5. 服务端与 OSS 公共改造

### 5.1 让客户端直连 OSS 媒体

卡片接口返回不同用途的短期签名地址：

```json
{
  "thumbnailUrl": "signed thumb-480 URL",
  "detailImageUrl": "signed detail-1280 URL",
  "originalDownloadUrl": "按下载操作临时获取",
  "videoPosterUrl": "signed poster URL",
  "videoStreamUrl": "signed original video URL"
}
```

页面展示直接使用 OSS HTTPS 地址。ECS 不再执行媒体代理，只保留以下职责：

- 验证当前用户是否拥有卡片。
- 生成 10-15 分钟有效的私有 OSS 签名地址。
- 原图下载时按请求重新生成短期地址。
- 删除资源时继续通过服务端校验并删除 OSS 对象。

在自定义 HTTPS 媒体域名和 CDN 未完成前，可保留配置开关：

```dotenv
MEDIA_DELIVERY_MODE=proxy   # 当前兼容路径
MEDIA_DELIVERY_MODE=oss     # OSS 签名直连
MEDIA_DELIVERY_MODE=cdn     # 后续 CDN 签名直连
```

### 5.2 保持视频 Range 能力

- 小程序和 Web 的 `<video>` 直接使用 `videoStreamUrl`。
- 播放页面不调用完整下载接口。
- 验收 OSS 返回 `Accept-Ranges: bytes`，分段请求返回 `206 Partial Content`。
- 保存到相册或浏览器下载时，才获取完整文件。
- 仅进入视口或打开详情时加载海报；视频本体在用户点击播放后才请求。

用户看完完整视频时，OSS 下行体积仍接近原文件；用户只试看一部分时，只消耗实际播放分片。无论是否看完，ECS 都不再重复承担同等体积的代理下行。

### 5.3 列表 DTO 与详情 DTO 分离

新增轻量列表模型，列表只返回：

- `id`、`type`、`weekId`、`dayIndex`、`createdAt`
- 最多 5 个标签
- 标题、摘要截断值
- `thumbnailUrl` 或 `videoPosterUrl`
- 组合卡图片数、视频记录数
- 收藏状态

列表不返回：

- 完整 `mdContent`
- 全部 `videoAssets`
- 全部 `imageAssets`
- 原图地址
- 组合详情数组

用户打开详情后，再请求 `/api/db/cards/:id` 和对应组合、视频、绑定图片接口。

### 5.4 API 与静态资源压缩缓存

- Express 增加 gzip/Brotli 响应压缩，覆盖 JSON、JS、CSS、SVG 和文本。
- Vite 哈希资源 `/assets/*` 设置 `Cache-Control: public, max-age=31536000, immutable`。
- `index.html` 使用短缓存或 `no-cache`，确保新版本能及时发现。
- 私有媒体签名 URL 使用不超过签名有效期的缓存时间。
- 保留 ETag 和 `Last-Modified`，减少重复传输。

## 6. 小程序专项方案

### 6.1 移除浏览场景的 `downloadAsset()`

以下页面展示图片时直接使用签名缩略图地址：

- `pages/diary`
- `pages/day-detail`
- `pages/search`
- `pages/books`
- `pages/me`
- `pages/card-detail`

`downloadAsset()` 只保留给“保存图片、保存视频”操作。这样图片组件可以按视口和缓存策略加载，避免 JavaScript 先把每张图片完整下载到临时文件。

### 6.2 页面数据拆分

#### 灵感首页

新增周摘要接口，一次只返回：

- 每天卡片数量。
- 每天最新 3 张 `thumb-240`。
- 本周总卡片数、MD 数和标签数。
- 灵感册最新若干封面。

首页不再请求 200 条完整卡片。

#### 日详情和灵感册

- 每页 20 条。
- 距离底部约 3-5 条时预取下一页。
- 首次只渲染第一页，其余使用分页游标或页码。

#### 搜索和收藏

- 搜索每页 20 条，输入停止 300ms 后请求。
- 收藏首屏 12 条，滚动后每次追加 12 条。
- 新请求开始时取消旧请求或忽略旧响应，避免重复下行。

### 6.3 图片组件策略

- 非首屏图片启用懒加载。
- 卡片容器保持固定尺寸，加载前显示本地占位色或骨架，不产生布局跳动。
- 首页第一张关键封面正常加载，后续图片懒加载。
- 图片加载失败时回退到本地占位图，不自动重试原图。
- 工具箱固定图片、默认头像和演示素材使用本地压缩资源，避免额外域名和重复网络流量。

### 6.4 小程序视频

- 列表只显示 `poster-720` 或更小海报。
- 打开详情后仍不下载视频；用户点击播放才由 `<video>` 请求 OSS Range。
- 不自动播放，不自动预取完整视频。
- “保存到相册”明确作为完整下载操作。
- 切出详情页时释放 video context，避免后台继续传输。

## 7. Web 专项方案

### 7.1 保留现有分页并补齐懒加载

“全部灵感”和灵感册目前每页 12 条，继续保留。调整图片策略：

- 普通 `PolaroidCard` 图片增加 `loading="lazy"` 和 `decoding="async"`。
- 组合封面、视频海报和绑定图片统一使用缩略规格。
- 首屏可见的前 2-4 张图片使用正常或高优先级加载，其余懒加载。
- 不在列表中请求详情大图。

### 7.2 当前周视图

当前周卡片数量较少时可一次加载元数据，但图片只加载可见卡片。如果单周数据增长，接口改为返回每天摘要和当前激活卡片；用户切换卡片时再加载对应缩略图。

### 7.3 图片详情

- 打开详情先展示卡片已有 `thumb-480`，同时加载 `detail-1280`。
- 中等图加载完成后无闪烁替换。
- 只有点击“下载原图”才获取 original 地址。
- 图片缩放检查器使用 `detail-1280`；当用户放大超过实际分辨率时，再提示或按需获取原图，而不是默认加载原图。

### 7.4 Web 视频

- 保留 `preload="metadata"` 和 `playsInline`。
- `src` 改为 OSS/CDN 签名流地址，不经 ECS。
- 列表只加载海报；弹出详情后再创建 `<video>`。
- 页面关闭或切换卡片时清空 `src` 并调用 `load()`，停止浏览器继续下载。
- 绑定视频列表默认只显示海报和文件信息，用户点击某条后再创建播放器，避免同一详情页同时初始化多个视频。

### 7.5 Web 上传

保留当前“原图上传 + 600px AI 分析副本”流程：

- 原图用于下载和后续高质量用途。
- 600px 副本只用于 AI 识别，避免把大图 Base64 发给模型。
- 上传完成后列表立即使用 `thumb-480`，不回读原图。
- 后续可改为客户端直传 OSS，服务端只签发上传凭证，减少 ECS 上行带宽；这属于第二优先级，不影响本次下行优化主线。

## 8. CDN 阶段

备案和 HTTPS 媒体域名完成后，将 OSS 作为阿里云 CDN 私有源站：

- 客户端从最近的 CDN 节点读取图片、海报和视频分片。
- CDN 缓存固定图片处理规格，减少 OSS 回源次数。
- 私有内容使用 CDN URL 鉴权或短期签名，不将 Bucket 改为公共读。
- 缓存键必须保留资源路径和图片规格；鉴权参数的缓存键处理按 CDN 私有内容规则配置，不能简单忽略全部查询参数。
- 微信后台分别配置 request、downloadFile、image 和 video 所需的合法 HTTPS 域名。

阿里云官方说明 CDN 可通过边缘缓存降低延迟和源站请求，并可能降低单位下行成本，但仍会产生 CDN 下行和 OSS 回源费用：

- [CDN 加速 OSS 资源](https://help.aliyun.com/zh/oss/user-guide/cdn-acceleration)
- [使用 CDN 加速 OSS 图片](https://help.aliyun.com/zh/cdn/use-cases/use-alibaba-cloud-cdn-to-accelerate-the-delivery-of-images-in-oss)

## 9. 分阶段实施顺序

### P0：视频和媒体直连

涉及：`server.ts`、OSS storage provider、小程序 `utils/api.js`、小程序卡片详情、Web 卡片详情。

1. API 返回 OSS 签名流地址和海报地址。
2. 视频播放移除完整预下载。
3. 图片、视频浏览流量绕过 ECS。
4. 保留代理模式开关用于回滚。

预期收益：ECS 媒体下行减少 90% 以上；视频首帧时间显著降低。

### P1：统一图片规格

1. 建立 `thumb-240`、`thumb-480`、`detail-1280`、`original`。
2. 主图、绑定图片和组合图片使用相同变体规则。
3. 列表不再获取原图。

预期收益：图片浏览流量减少约 60%-90%，取决于原图尺寸和页面结构。

### P2：小程序页面按需加载

1. 新增周摘要接口。
2. 日详情、搜索、灵感册、收藏分页。
3. 移除浏览场景 `downloadAsset()`。
4. 图片懒加载、骨架和下一页预取。

预期收益：小程序首屏媒体请求量减少 70% 以上，卡片多时收益更高。

### P3：Web 细化

1. 补齐图片 lazy/async 解码。
2. 图片详情渐进加载。
3. 多视频详情改为点击后才创建播放器。
4. 列表 DTO 瘦身、API 压缩和静态资源长期缓存。

### P4：CDN

1. 配置已备案 HTTPS 媒体域名。
2. CDN 私有回源 OSS。
3. 设置图片规格、视频分片和静态资源缓存规则。
4. 根据真实账单和命中率调整缓存 TTL。

## 10. 验收指标

### 流量

- 页面浏览不自动请求原图。
- 小程序首页首次媒体下行目标不超过 800 KB。
- Web 首屏媒体下行目标不超过 1.2 MB。
- ECS 媒体字节下行相较改造前减少至少 90%。
- 缩略图单张大多数低于 100 KB，详情图大多数低于 350 KB。

### 体验

- 4G 环境视频点击到首帧 P75 小于 2 秒。
- 图片首屏可见内容 P75 小于 1.5 秒。
- 图片切换和分页过程中不出现明显布局跳动。
- 原图下载结果与上传原文件一致。
- 视频拖动进度条可触发 206 分段请求并正常跳播。

### 稳定性

- OSS/CDN 签名过期后可重新获取，不出现永久坏链接。
- 媒体域名失败时可通过配置切回 ECS 代理。
- 删除、收藏、账号隔离和灵感册权限不因直连媒体而改变。

## 11. 监控与成本核对

上线前后分别记录 7 天：

- OSS 外网流出 GB、GetObject 次数和图片处理次数。
- ECS 出网 GB、带宽峰值和 `/api/videos`、`/api/images` 传输字节。
- CDN 下行 GB、回源 GB、命中率和 4xx 比例。
- 小程序各页面首屏请求数、下行字节和图片失败率。
- Web Resource Timing 中图片、视频首帧和详情加载耗时。

成本评估不能只看 OSS 流量：OSS 图片处理和 CDN 也会计费，应以“OSS 流出 + 图片处理 + CDN 下行 + CDN 回源 + ECS 出网”的总成本对比为准。

## 12. 推荐落地结论

最先实施 P0 和 P1。当前最大问题是视频完整下载与 ECS 二次代理，而不是图片压缩参数本身。先把媒体流改成 OSS 签名直连和视频 Range 播放，再统一图片规格；随后做小程序周摘要、分页和懒加载。CDN 应在 HTTPS 媒体域名就绪后接入，不应阻塞前两阶段。
